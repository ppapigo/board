# 인증과 권한

## 토큰 모델

- Access token: JWT, 설정상 1시간. 보호 API에 `Authorization: Bearer <token>`으로 전송한다.
- Refresh token: 불투명 UUID, 설정상 10시간. DB에 사용자당 하나를 보관한다.
- Refresh cookie: `refreshToken`, HttpOnly, path `/api/auth`, 개발 환경 `Secure=false`, `SameSite=Strict`.
- 로그인 응답의 `accessToken`은 현재 `Bearer ` 접두사를 포함한다.
- 재발급 응답의 `accessToken`은 현재 접두사를 포함하지 않는다. 프런트엔드는 이 불일치를 임시 정규화해야 하며 서버 계약 통일이 권장된다.

## 로컬 로그인 흐름

1. `POST /api/auth/login`에 email/password를 보낸다.
2. 응답 body의 access token을 메모리 중심으로 보관한다.
3. 서버는 refresh token을 HttpOnly cookie로 함께 설정한다.
4. API가 401이면 `POST /api/auth/reissue`를 credentials 포함으로 한 번 호출한다.
5. 성공 시 원 요청을 한 번 재시도하고, 실패하면 인증 상태를 제거해 로그인으로 보낸다.
6. 로그아웃은 `POST /api/auth/logout`으로 서버 토큰과 쿠키를 만료시킨다.

## OAuth 흐름

현재 두 구현이 공존한다.

- 직접 Kakao: `/api/oauth/kakao/login` → Kakao → `/api/oauth/kakao/callback`; callback이 JSON을 반환한다.
- Spring Security OAuth2: `/oauth2/authorization/{kakao|google}` → provider callback; 성공 handler가 JSON을 반환한다.

두 방식 모두 일반 브라우저 리다이렉트 최종 화면에 JSON이 노출될 가능성이 있다. 프런트엔드 callback URL로 안전하게 토큰을 전달하는 목표 흐름을 먼저 결정해야 한다. [[08-결정사항과-알려진-이슈]] 참고.

## 클라이언트 보안 요구사항

- refresh token은 JavaScript로 읽지 않고 cookie에 맡긴다.
- access token, 비밀번호, OAuth code를 로그에 남기지 않는다.
- cookie 기반 요청에는 `credentials: 'include'`를 사용한다.
- 현재 CORS 설정이 명시되어 있지 않으므로 프런트와 API origin이 다르면 서버 설정이 필요하다.
- 회원가입 화면에서 `ADMIN` 역할을 선택하게 해서는 안 된다. 서버도 공개 요청의 role 승격을 차단해야 한다.
