# 프런트엔드 요구사항

이 문서는 현재 API로 구현 가능한 MVP와 서버 보완이 필요한 요구사항을 구분한다. `MUST/SHOULD/COULD`는 우선순위다.

## 제품 목표

사용자는 로그인 여부와 무관하게 콘텐츠를 빠르게 탐색하고, 로그인 후 작성·상호작용·알림 확인을 끊김 없이 수행할 수 있어야 한다.

## 정보 구조와 라우트 제안

| 화면 | Route | 접근 | 핵심 데이터 |
|---|---|---|---|
| 홈/게시판 목록 | `/` | 공개 | boards, 최근 posts |
| 게시판 글 목록 | `/boards/:boardId` | 공개 | board, paged posts |
| 게시글 상세 | `/posts/:postId` | 공개 | post, comments |
| 글쓰기 | `/boards/:boardId/new` | 인증 | multipart create |
| 글 수정 | `/posts/:postId/edit` | 작성자 | post update |
| 로그인 | `/login` | 공개 | local/OAuth login |
| 회원가입 | `/signup` | 공개 | signup |
| 알림 | `/notifications` | 인증 | notification page/count |
| 내 프로필 | `/me` | 인증 | profile |
| 게시판 관리 | `/admin/boards` | ADMIN | board CRUD |

## 핵심 사용자 스토리

### 탐색

- MUST 게시판 목록을 조회하고 게시판별 글 목록으로 이동한다.
- MUST 글 목록에 제목, 작성자, 작성 시각, 조회수를 표시한다.
- MUST 페이지 이동과 로딩/빈 목록/오류 상태를 제공한다.
- SHOULD 게시판·페이지 상태를 URL에 유지한다.

### 게시글

- MUST 상세에서 제목, 작성자, 본문, 이미지, 조회수, 반응 수를 표시한다.
- MUST 인증 사용자는 제목 5~200자와 필수 본문으로 글을 작성한다.
- MUST 이미지 0~5개를 선택하고 미리보기·제거·순서 확인 후 업로드한다.
- MUST 작성자에게만 수정/삭제 UI를 노출한다. `canEdit`, `canDelete`를 우선 사용한다.
- MUST 삭제 전에 확인하고 성공 후 해당 게시판 목록으로 이동한다.
- SHOULD 업로드 제한(허용 형식, 파일당 2MB)을 제출 전에 검증한다.

### 댓글과 답글

- MUST 루트 댓글을 페이지 단위로 표시하고 댓글/답글 작성, 본인 댓글 수정·삭제를 제공한다.
- MUST 댓글은 공백 제외 1~100자로 검증한다.
- MUST 답글은 루트 댓글에만 허용하며 삭제 댓글에는 답글 버튼을 숨긴다.
- MUST 삭제 댓글은 자리와 답글 맥락을 유지한다.
- BLOCKED 중첩 `children` 응답 계약이 확정되기 전에는 답글 렌더링을 신뢰성 있게 구현할 수 없다.

### 반응

- MUST 로그인 사용자가 LIKE/DISLIKE를 토글하거나 전환할 수 있다.
- MUST 서버 응답의 최신 count와 `myReaction`으로 즉시 상태를 동기화한다.
- SHOULD 비회원 클릭 시 현재 위치를 보존한 채 로그인으로 유도한다.

### 인증

- MUST 새로고침 후 refresh cookie로 세션을 복원한다.
- MUST 401에 대해 재발급은 동시에 한 번만 실행하고 원 요청은 최대 한 번 재시도한다.
- MUST 인증 필요 route와 ADMIN route를 보호한다.
- MUST 로그아웃 후 토큰 캐시와 사용자 상태를 제거한다.
- MUST 회원가입 UI에서 role을 받지 않고 항상 일반 사용자로 요청한다(서버 수정 전 임시값 `USER`).
- BLOCKED OAuth 완료 후 프런트로 복귀하는 표준 callback 계약이 필요하다.

### 알림과 프로필

- MUST 헤더에 미읽음 개수를 표시한다.
- MUST 알림 목록에서 읽음/미읽음을 구분하고 클릭 시 게시글로 이동하며 읽음 처리한다.
- SHOULD 알림 기본 정렬을 최신순으로 요청한다.
- MUST 프로필에서 닉네임, 전화번호, 생일, 가입일을 읽기 전용으로 표시한다.

### 관리자

- MUST ADMIN에게만 게시판 관리 진입점을 노출한다.
- MUST 게시판 생성·수정 시 이름 필수, 삭제 시 확인을 제공한다.
- BLOCKED 현재 로그인 응답의 `role`이 채워지지 않아 안정적인 ADMIN UI 판별 계약이 필요하다.

## 공통 UX 요구사항

- 모든 비동기 화면에 loading, empty, error, success feedback을 제공한다.
- 오류는 HTTP status보다 `ErrorResponse.code`를 우선 분기하고 사용자 친화적 문구로 매핑한다.
- destructive action은 확인 대화상자를 사용하고 중복 제출을 막는다.
- 키보드만으로 주요 기능을 수행할 수 있고 입력에는 label, 오류에는 접근 가능한 설명이 있어야 한다.
- 모바일 360px부터 데스크톱까지 반응형이어야 한다.
- 이미지에는 대체 텍스트 전략을 둔다. 현재 API에 alt text가 없으므로 원본 파일명을 임시 사용한다.
- 날짜 parser는 offset 없는 서버 시간을 한국 시간 기준으로 취급한다는 임시 정책을 명시한다.

## 클라이언트 상태 제안

- 서버 상태: boards, post pages, post detail, comments, reactions, notifications, profile
- 인증 상태: user identity, access token, restore status
- 로컬 UI 상태: editor draft, selected files, dialogs
- mutation 성공 시 관련 query를 무효화하고, 반응처럼 응답이 완전한 경우 반환값으로 캐시를 갱신한다.

## 완료 조건

- 핵심 route의 정상/로딩/빈 상태/오류/권한 없음 상태가 구현되어 있다.
- 새로고침 및 access token 만료 후에도 인증 흐름이 복구된다.
- 실제 API를 대상으로 회원가입→로그인→글→댓글→반응→알림 흐름이 검증된다.
- [[08-결정사항과-알려진-이슈]]의 P0가 해결되거나 승인된 임시 정책으로 기록된다.
